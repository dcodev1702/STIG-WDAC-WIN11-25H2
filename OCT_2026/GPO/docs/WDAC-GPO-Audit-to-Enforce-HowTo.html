Deploy App Control with two GPOs: Audit first, then Enforce

This guide takes you from an approved App Control base policy to an Enforce GPO that is linked and enabled on your PAW OU. It uses the scripts in OCT_2026/GPO/scripts (steps 0 to 6). Each step tells you what to run, what it does, what you should see when it finishes, and what to do if you see something else. When you finish, the PAWs enforce App Control in both kernel and user mode, and both App Control checks of the Microsoft Windows PAW STIG are Not a Finding.

1The STIG requirements this satisfies

Both requirements come from the Microsoft Windows Privileged Access Workstation (PAW) STIG. Each needs an App Control (formerly WDAC, Device Guard code integrity) policy that is enforced on the PAW. They are checked separately: kernel mode and user mode must each read 2.

Vuln IDSTIG IDSeverityRequirementWhat is checkedPasses when
V-243450WPAW-00-001050CAT IIDevice Guard Code Integrity Policy: the PAW must have an App Control code integrity policy deployed and active to restrict which applications can run.Win32_DeviceGuard → CodeIntegrityPolicyEnforcementStatus (kernel mode)2 (Enforced)
V-243451WPAW-00-001060CAT IIDevice Guard User Mode Code Integrity (UMCI): the same requirement, verified separately for user mode. UMCI must be enforced, not just kernel mode.Win32_DeviceGuard → UsermodeCodeIntegrityPolicyEnforcementStatus (user mode)2 (Enforced)

Values: 0 = Not configured (finding) · 1 = Audit (still a finding) · 2 = Enforced (Not a Finding).

    Format-List CodeIntegrityPolicyEnforcementStatus, UsermodeCodeIntegrityPolicyEnforcementStatus

2How the solution works (read this once)

Reference deviceYour approved policy Base-Enforce.xml + PolicyGuid.txt
→
Step 1: buildTwo compiled packages from the same XML: Audit vN and Enforce vN+1
→
Step 2: two GPOsPackages copied to each GPO's SYSVOL folder; both linked to the OU, links disabled
→
Step 3: one link onAudit first, then Enforce. Never both.
→
EndpointsA startup script + scheduled task (SYSTEM) deploy the {GUID}.cip with CiTool
Design ruleWhy it matters to you
Both packages carry the same policy GUIDEnforce replaces Audit in place. There's never a second base policy.
Enforce version = Audit version + 1Switching Audit → Enforce is just a link switch. No reboot needed.
Endpoints never downgradeGoing back from Enforce to Audit needs a new, higher-versioned pair (Day-2). Flipping the link back alone does nothing.
Only one link enabled at a timeStep 3 disables before it enables; step 4 fails if both are on.
Disabling or deleting a GPO never removes the policy from devicesRemoval is an explicit step (step 6).
Versions are date-based: YYYY.MM.DD.NStep 1 always picks a version above every version it knows, including what's already published in both GPOs, so endpoints always accept it.
Delivered by a script inside the GPO, not the built-in "Deploy App Control" settingThat built-in setting only supports the legacy single-policy format (SiPolicy.p7b). Multiple-policy {GUID}.cip files need CiTool, which runs as SYSTEM from the GPO.
Keep the target computers out of any legacy "Deploy App Control for Business" GPO.A legacy single policy and this multiple-policy base policy would both be active and would intersect: a file would need to pass both.

Order of the steps (the numbers are the script names; 4 runs before 3 on purpose):

0 pre-flight → 1 build → 2 create GPOs → 4 validate GPOs → 3 Audit → 5 validate endpoints
   → audit period (fix gaps: 1 → 2 → 4) → 3 Enforce → 5 validate endpoints → reboot → 5 again

4Prepare the reference device

4.1 Folder layout

C:\WDAC\
  Source\            Base-Enforce.xml   PolicyGuid.txt   (Base-Audit.xml optional, for reference)
  GPO\
    scripts\         the OCT_2026\GPO\scripts files (0_ ... 6_, Deploy-WDACPolicy.ps1, GPO-Settings.psd1, helpers)
    Packages\        created by step 1 (one time-stamped folder per build)
    Logs\            created by every step: transcript (.log) + PASS/WARN/FAIL table (.csv)

4.2 Copy the scripts, unblock them, allow them for this session

# elevated PowerShell (Windows PowerShell 5.1 or PowerShell 7)
New-Item -ItemType Directory -Force C:\WDAC\Source, C:\WDAC\GPO\scripts | Out-Null
Copy-Item '<path to repo>\OCT_2026\GPO\scripts\*' C:\WDAC\GPO\scripts\ -Recurse -Force
Get-ChildItem C:\WDAC -Recurse | Unblock-File
Set-ExecutionPolicy -Scope Process Bypass -Force     # this window only
Set-Location C:\WDAC\GPO\scripts

If PowerShell says "running scripts is disabled on this system", you skipped the Set-ExecutionPolicy -Scope Process line. Run it in every new window.

4.3 Put the policy in place and check it

Copy your approved policy to C:\WDAC\Source\Base-Enforce.xml. The build in step 1 makes both packages from this one file: the Audit package is the same rules with Audit Mode switched on.

$x = [xml](Get-Content C:\WDAC\Source\Base-Enforce.xml -Raw); $o = @($x.SiPolicy.Rules.Rule.Option)
[pscustomobject]@{
  PolicyID = $x.SiPolicy.PolicyID; BasePolicyID = $x.SiPolicy.BasePolicyID; Type = $x.SiPolicy.PolicyType; Version = $x.SiPolicy.VersionEx
  UMCI = ($o -contains 'Enabled:UMCI'); AuditMode = ($o -contains 'Enabled:Audit Mode'); ManagedInstaller = ($o -contains 'Enabled:Managed Installer') } | Format-List
Get-Content C:\WDAC\Source\PolicyGuid.txt
You should see
  • PolicyID = BasePolicyID = the GUID in PolicyGuid.txt (with braces), and Type = Base Policy
  • UMCI = True: required for V-243451. Without option 0 Enabled:UMCI, user mode is never checked.
  • AuditMode = False: the source must be the enforced policy.
  • ManagedInstaller = True: recommended (MECM installs).
If not 
# PolicyGuid.txt missing: create it from the XML
([xml](Get-Content C:\WDAC\Source\Base-Enforce.xml -Raw)).SiPolicy.PolicyID | Set-Content C:\WDAC\Source\PolicyGuid.txt -NoNewline
# You only have an audit-mode XML (e.g. Base-Audit.xml): make the enforced copy
Copy-Item C:\WDAC\Source\Base-Audit.xml C:\WDAC\Source\Base-Enforce.xml
Set-RuleOption -FilePath C:\WDAC\Source\Base-Enforce.xml -Option 3 -Delete
Updating policies you already deployed?Keep the same PolicyID. Endpoints replace a policy in place only when the GUID matches, and steps 0 and 1 refuse an XML whose GUID differs from PolicyGuid.txt.
FilePath rules must point to admin-only folders.Windows ignores a FilePath rule if standard users can write to its folder (runtime FilePath rule protection). Never use paths under C:\Users\<name>\: step 1's portability gate refuses them. Steps 0 and 5 warn about rule folders that are missing or user-writable.

Common warnings (OK to continue)
  • FilePath folder … does not exist on this computer: the app isn't installed on the reference device. The rule still works on PAWs where it is installed.
  • FilePath folder … is writable by …: Windows will ignore that rule on devices with the same image, so those files will be blocked under Enforce. Fix the folder ACL in the image, or allow those files by publisher or hash.

Build the Audit and Enforce packages

reference device · local files only
Run 
.\1_GPO_build_packages.ps1
What it does
  1. Picks versions: today's YYYY.MM.DD.N for Audit and N+1 for Enforce, always above every version it knows.
  2. Builds two copies of Base-Enforce.xml: Audit (option 3 Audit Mode added) and Enforce (option 3 removed). Each is stamped with name <prefix>-Audit|Enforce, ID GPO-AUDIT|ENFORCE-<version> and its version.
  3. Gate, before anything compiles: same GUID, both base policies, options differ only by Audit Mode, and the rule sections (EKUs, FileRules, Signers, SigningScenarios, CiSigners) are byte-identical. It also runs the portability check.
  4. Compiles each into C:\WDAC\GPO\Packages\<stamp>\Audit|Enforce\{GUID}.cip, with a manifest.json (versions, SHA-256, FilePath rules) and a copy of Deploy-WDACPolicy.ps1. The exact XML behind each package is kept in Packages\<stamp>\xml\.

  • WDAC-GPO-Deploy-Audit not present: the PAW hasn't refreshed yet. Run gpupdate /target:computer /force on it and wait about 2 minutes.
  • Applied GPOs missing the WDAC GPO: the computer isn't in the OU, the link is disabled, or security filtering excludes it.
  • WinRM … Cannot find the computer: run step 5 on the PAW itself without -ComputerName.

12The audit period: find what Enforce would block

In Audit nothing is blocked; Windows logs Event 3076 for every file the policy would block. Let users run every application and workflow for a full work cycle: logon (CAC/smart card), browsers, admin tools, agents (EDR, SIEM, scanners), printing and VPN.

Review what would be blocked

# on a PAW (or wrap in Invoke-Command -ComputerName PAW01 { ... })
$since = (Get-Date).AddDays(-7)
Get-WinEvent -FilterHashtable @{ LogName = 'Microsoft-Windows-CodeIntegrity/Operational'; Id = 3076; StartTime = $since } |
  ForEach-Object { $d = @{}; ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{ File = ($d['File Name'] -replace '^\\Device\\HarddiskVolume\d+', 'C:'); Process = ($d['Process Name'] -replace '.*\\', '')
                       Policy = $d['PolicyName']; UserWriteable = $d['UserWriteable'] } } |
  Group-Object File | Sort-Object Count -Descending | Select-Object Count, Name
You find…Do this
An approved app is flaggedAdd a rule to Base-Enforce.xml, keeping the same PolicyID. Prefer a publisher rule for signed code; a FilePath rule only for admin-only install folders (check UserWriteable = false in the event); a hash rule as a last resort. Then republish: 1 → 2 → 4. PAWs in Audit move to the new, higher Audit version on their own.
Something that should never runNothing to do. Enforce will block it.
MSI setup DLLs (MSIxxxx.tmp in C:\Windows\Installer or %TEMP%)Installer helpers from manual installs. Deploy software with MECM as managed installer; don't allow these by path.
A file blocked by an explicit deny rule (3089 VerificationError 26)Deny rules always win over allow rules. Allowing the file means removing the deny rule, which is a security decision; document it.
Ready to enforce when…a full work cycle produces no 3076 for anything you need. Pick an app you deliberately don't allow as your known-block test for step 5, for example a browser that isn't on the approved list.

Enforce · step 3

Switch the OU to Enforce

reference device · enables the Enforce link · asks Y/N
Run 
.\3_GPO_set_mode.ps1 -Mode Enforce -GpUpdate
What it does

It disables the Audit link and enables the Enforce link. At each PAW's next refresh, Group Policy removes the WDAC-GPO-Deploy-Audit task and creates WDAC-GPO-Deploy-Enforce. About a minute later that task deploys Enforce vN+1 over Audit vN in place, with no reboot.

TaskHowWhat happens on the PAWs
Publish an updated policy (same mode)Update C:\WDAC\Source\Base-Enforce.xml (same PolicyID), then .\1_GPO_build_packages.ps1 → .\2_GPO_create_gpos.ps1 → .\4_GPO_validate_gpos.ps1They move to the new, higher version in place at the next refresh, within TaskIntervalHours, or at boot. Add a PAWMove the computer account into the target OU; reboot it or run gpupdate /target:computer /forceIt gets whichever mode is enabled

Demote Enforce → AuditDo it in this order: (1) .\3_GPO_set_mode.ps1 -Mode Audit (it warns: expected), (2) .\1_ → .\2_ → .\4_ (a new, higher pair), (3) .\5_They move from Enforce vN+1 to the new Audit version in place. Back to Enforce.\3_GPO_set_mode.ps1 -Mode EnforceIn place: the new Enforce version is higher
Why switch first when demoting?If you publish while the Enforce link is still on, a PAW that refreshes in between takes the new, higher Enforce version and then ignores the new Audit one.
